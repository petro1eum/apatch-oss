# Avatar Utility Contract (AUC-1)

> **Статус:** Contract v1.0 · 2026-07-10. **Подчинён** [Avatar Architecture Canon](./AVATAR-ARCHITECTURE-CANON.md):
> онтологию сущностей (`Avatar`, `ContributionEvent`, `Identity`) этот документ **не переопределяет** — при
> конфликте определений побеждает канон. Здесь фиксируется другое: **потребительский контракт полезности** —
> что аватар *делает* для владельца каждый рабочий день, кто это исполняет и по какому контракту данных.
> Это не vision-документ: каждая секция либо контракт, либо требование с критерием приёмки.

---

## 0. Зачем этот документ существует

Построены паспорт, доказательная база и каталог: свёртка фактов (канон §6), `asset_summary`,
timesheet, публичный профиль, витрина WorkAsset. Всё это — функции **доказательства**, потребляемые
редко (найм, трансфер, спор). Механизм, который превращает накопленный опыт в **помощь во время
следующей задачи**, отсутствует. Документально:

- Канон определяет Avatar только как свёртку фактов (`AVATAR-ARCHITECTURE-CANON.md` §6) — намеренно; это память+доказательство, не движок.
- ADR-007 (HC) называет «ежедневной пользой» рост/портативность/доказательства — это накопление и просмотр, не помощь в работе.
- `SPEC-WORK-ASSET-INDEX-1` «deliberately stops before promotion, reuse tracking, suggestion/apply».
- `apatch/work_assets.py`: `reuse.count ≡ 0`, поиск — совпадение слов (`_score_asset`).
- Нужный цикл уже расписан как фазы 2–5 RFP-031 — но не реализован и не был сформулирован как функция аватара.

**Утренний тест (критерий полезности):** *убери аватар — что сломается завтра утром?*
Сегодня: ничего (пострадает только будущий трансфер). Цель контракта: подключённый AI владельца
становится заметно хуже, потому что теряет его накопленную методологию.

## 1. Формула полезности (одна фраза)

> **Любой подключённый AI начинает работу не с пустого листа, а с проверенных методов этого человека,
> знает границы их применимости — и после выполнения возвращает подтверждённый результат обратно
> в его профессиональную память.**

---

## 2. Разделение сущностей — никто не переопределяет чужое (канон R4)

| Сущность | Что это | Слой/владелец | Чем НЕ является |
|---|---|---|---|
| **Avatar** | Доверенная портативная память и доказательство человека (свёртка фактов) | L2 · apatch Avatar Compiler (+HC хранение) | не движок, не агент, не PI |
| **WorkAsset** | Проверенный способ решать определённый класс задач | L1 · apatch (RFP-031) | не карточка-витрина без процедуры (§5) |
| **Concept Graph** | Карта понятий, зависимостей и ограничений | L1-индекс · apatch (RFP-034) | не wiki-проза |
| **Avatar Recall** | Сервис: находит подходящую наработку для текущей задачи | L2 read-проекция · apatch | ничем не владеет, ничего не мутирует |
| **AI-агент** | Применяет наработку через governed-сессию | L4 · TrustChain Agent / IDE-MCP | не хранит доменных сущностей |
| **Avatar Home** | Показывает, контролирует доступ, объясняет результат | L4 · `trust-chain.ai` canonical web + HC Tracker native/mobile | не compute-plane |

## 3. Ежедневный цикл (recall → use → verify → learn)

```text
новая задача
    ↓
Avatar Recall понимает контекст (intent)
    ↓
1–3 подходящие ПРОВЕРЕННЫЕ наработки  →  компактный RecallBundle
    ↓
AI-агент применяет или адаптирует метод (обычная governed-сессия)
    ↓
verify + attest                       (без обхода: канон L1)
    ↓
WorkAssetUseEvent (+результат проверки) → леджер
    ↓
память обновлена: reuse, recency, границы применимости → следующий recall умнее
```

Инвариант направления: **Recall читает, никогда не пишет.** Единственный способ изменить память —
подписанный факт (use event через verify+attest). Suggestion не обходит сессии, верификацию и
аттестацию (RFP-031 Phase 3, дословно).

## 4. RecallBundle v1 — контракт данных

Гигабайты не переносятся. Bundle — **дистиллят с доказательствами**, а не архив:

| Поле | Содержимое |
|---|---|
| `why_fit` | почему наработка подходит этой задаче (совпадение intent/контекста, класс задач) |
| `method` | процедура — или **разрешённый политикой указатель** на неё (content-safe, политики RFP-031) |
| `context` | необходимый контекст и **противопоказания** (границы применимости, анти-паттерны) |
| `evidence` | проверки и доказательства: verify-команды, `proof_ref`/аттестации, история re-verify |
| `rights` | зависимости, права, портабельность (portability class) |
| `next_action` | следующий **governed** шаг (spec run / apply session) — не «сделай сам как-нибудь» |

**Инварианты bundle:** (1) money-free — экономический барьер канона §7.3, сканирование как в
`avatar_contract.assert_economic_barrier`; (2) content-safe — никаких секретов/исходников сверх
разрешённого указателя; (3) компактность — бюджет ≤ 16 KB на bundle; (4) детерминизм — тот же
леджер + тот же intent → тот же bundle; (5) scope = `ledger` — кросс-проектно по `key_id` одной
identity (как `avatar_compiler`).

---

## 5. Известный дефект — WorkAsset без процедуры

RFP-031 называет WorkAsset «исполняемым описанием метода», но текущая схема — карточка: название,
теги, ссылки, proof refs. **Самой процедуры нет** — по такому ассету нельзя профессионально
выполнить работу без повторного чтения исходных документов.

**R-AUC-1:** у recall-able (promoted) наработки поле `method` обязательно — процедура + проверки +
противопоказания, либо content-safe указатель. Ассет без `method` показывается в Avatar Home, но
**не участвует в recall**.

**R-AUC-2:** `reuse.count` считается только из ledger-backed use records (Phase 2), не из константы.

## 6. Путь реализации — фазы уже предусмотрены RFP-031

| Шаг | Где | Приёмка |
|---|---|---|
| Lifecycle + ручное принятие качественных ассетов | `SPEC-WORK-ASSET-LIFECYCLE-1` (Phase 2) | promoted-состояния в леджере; use records подписаны |
| Полноценное содержимое метода (`method`) | расширение схемы INDEX-1 + R-AUC-1 | promoted-ассет без `method` невозможен |
| Intent-based recall/suggest | `SPEC-WORK-ASSET-SUGGEST-1` (Phase 3) | intent → топ-k RecallBundle; не обходит governed-цикл |
| Governed применение и адаптация | там же (Phase 3) | `next_action` ведёт в обычную сессию |
| `WorkAssetUseEvent` с результатом проверки | Phase 2/3 | событие в леджере, влияет на ранжирование |
| Поиск по всем проектам одной identity | scope=`ledger` по `key_id` | recall видит наработки из всех репо владельца |
| Автоподключение recall через MCP | MCP-инструмент (`apatch_work_asset_*` семейство) | агент получает bundle без ручных шагов |
| Обратная связь в Avatar Home | `SPEC-AVATAR-WORK-ASSETS-1` (Phase 5, HC) | владелец видит: что применялось, с каким результатом |

**Метрики приживаемости:** `reuse.count > 0` на реальных сессиях; доля задач, начатых с RecallBundle;
время до первого verified-шага с bundle vs без.

---

## 7. Не-цели

- **Не** переопределяет Avatar/ContributionEvent/Identity — онтология остаётся за каноном.
- **Не** добавляет экономику в свёртку или bundle (PI/GPI — L3, HC).
- **Не** новый рантайм: Recall — read-проекция в apatch; исполнение — существующие L4-поверхности.
- **Не** автоматизация решений: применить/адаптировать/отклонить решает человек+агент в governed-цикле.

---

## 8. Экономическое следствие

L3-экономика (Creator Bonus, PI-split) **предполагает**, что аватар ценен. Обоснованной её делает
именно функция-инструмент: компания платит, потому что человек приходит с работающим инструментарием,
а не за криптографически заверенное резюме. Без цикла recall → use → verify → learn экономика
аватара опирается на обещание будущей ценности, а не на наблюдаемую ежедневную пользу.
