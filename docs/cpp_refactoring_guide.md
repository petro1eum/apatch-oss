# Практическое руководство по C++ рефакторингу монолитов с apatch 🛠️🦕

Это руководство содержит специализированные прикладные рецепты и лучшие практики для компилируемых языков (на примере C++ проекта `ProbStates` и компилятора `O-Lang`), помогающие связать процесс автоматического вырезания кода (`apatch strip`) с системами сборки и компиляторами.

---

## 1. Регистрация исходных файлов в CMake

Когда `apatch strip` извлекает функции или ветки логики в новые файлы (например, в папку `src/extracted/`), проект перестанет собираться, пока эти файлы не будут зарегистрированы в компиляторе.

Использование `extraction_report.json` позволяет автоматизировать этот шаг.

### Регистрация исходников:
Скрипт автоматизации или ИИ-агент считывает `extraction_report.json`, парсит массив `extracted_blocks` и динамически обновляет `CMakeLists.txt` проекта:

```cmake
# Добавление исходников в таргет библиотеки или исполняемого файла
target_sources(olang_interpreter_core PRIVATE
    src/frontend/interpreter/eval_visitor.cpp
    
    # Новые извлеченные файлы (зарегистрированы после strip)
    src/extracted/native_eval_omega_head.cpp
    src/extracted/native_eval_reservoir.cpp
)
```

## 2. Подключение заголовочных файлов и замена заглушек

При вырезании реализации функций родительскому файлу всё еще нужно видеть их объявления. Вы можете использовать параметр `--replace` или поле `"replace"` в манифесте для автоматической вставки директив `#include`:

### Схема интеграции:
1. **Заглушка как инклуд**: В манифесте рефакторинга вместо текстового комментария укажите директиву включения будущего файла заголовков:
   ```json
   "replace": "#include \"extracted/native_eval_omega_head.h\"\n"
   ```
2. **Генерация интерфейса**: Создайте в папке экспорта файл `native_eval_omega_head.h`, объявив в нём прототипы вынесенных свободных функций:
   ```cpp
   #pragma once
   #include "eval_visitor.h"

   namespace olang {
       bool evaluate_omega_head(Interpreter& interp, CallExpr* call);
   }
   ```
3. **Настройка путей поиска в CMake**: Чтобы компилятор находил заголовочные файлы в папке экспорта, добавьте её в пути поиска инклудов таргета:
   ```cmake
   target_include_directories(olang_interpreter_core PRIVATE 
       ${CMAKE_CURRENT_SOURCE_DIR}/src/extracted
   )
   ```

## 3. Разрешение циклических зависимостей (Circular Dependencies)

Если вынесенный свободный метод в файле `native_eval_omega_head.cpp` обращается к членам класса `Interpreter`, а сам класс `Interpreter` должен вызывать этот вынесенный метод, возникает риск циклического включения заголовочных файлов (`#include` друг друга).

### Золотые правила борьбы с циклами при декомпозиции:
1. **Используйте опережающие объявления (Forward Declarations)**: 
   В новом заголовочном файле `native_eval_omega_head.h` вместо инклуда `#include "interpreter.h"` напишите простое объявление класса:
   ```cpp
   namespace olang {
       class Interpreter; // Опережающее объявление
       class CallExpr;
       
       bool evaluate_omega_head(Interpreter& interp, CallExpr* call);
   }
   ```
2. **Передавайте контекст аргументом**:
   Всегда передавайте ссылку или указатель на родительский объект (`Interpreter& interp` или `this`) в качестве первого аргумента свободной функции, чтобы она имела доступ к контексту исполнения.
3. **Импортируйте детали в `.cpp`**:
   Полный `#include "interpreter.h"` подключайте строго внутри файла реализации `native_eval_omega_head.cpp`. К этому моменту компилятор уже знает размер типов, и циклическая зависимость разрывается.

## 4. Доступ к приватным членам класса (friend в C++)

При ООП-декомпозиции вынесенный код очень часто пытается обратиться к приватным (`private` или `protected`) переменным и методам родительского класса (например, `Interpreter::strict_contracts_` или `Interpreter::chess_`).

Если просто вынести код, компилятор выдаст ошибку:
```
error: 'strict_contracts_' is a private member of 'olang::Interpreter'
```

### Три пути решения проблемы:

#### Вариант А. Дружественные функции (`friend`) — Рекомендуется 🌟
Этот метод сохраняет полную инкапсуляцию класса для всего внешнего мира, но открывает доверенный доступ конкретным вынесенным функциям.

Объявите свободную функцию другом класса внутри тела этого класса:
```cpp
// В файле include/frontend/interpreter.hpp:
namespace olang {
    // Опережающее объявление свободной функции
    class CallExpr;
    bool evaluate_omega_head(class Interpreter& interp, CallExpr* call);

    class Interpreter {
    public:
        // ...
        
        // Объявление другом класса: дает функции доступ к private членам
        friend bool evaluate_omega_head(Interpreter& interp, CallExpr* call);
        
    private:
        bool strict_contracts_ = true;
    };
}
```

#### Вариант Б. Публичные константные геттеры
Если свойство класса полезно и в других местах, создайте для него безопасный публичный метод чтения:
```cpp
public:
    bool is_strict_contracts() const { return strict_contracts_; }
```

#### Вариант В. Минимизация передаваемого контекста
Если выносимой логике нужно всего одно значение, не передавайте весь объект `Interpreter`. Передайте только нужное значение по ссылке/значению:
```cpp
// Было:
bool evaluate_omega_head(Interpreter& interp, CallExpr* call);

// Стало:
bool evaluate_omega_head(bool is_strict, CallExpr* call);
```
Это делает вынесенный модуль полностью независимым от родительского класса!
