## Позиционирование

**apatch — governed transformation runtime** (build orchestrator с cryptographic provenance), не gcc/clang и не «AI coding platform».

**Наиболее точная формулировка для сравнения с компилятором:**

> apatch относится к **agent intent** так же, как **build system** относится к **source code**.

Не «apatch is a compiler», а governed pipeline над **state transition** репозитория.

Основной актив — не патчи как such, а цепочка:

```text
Intent → Transformation → Verification → Provenance
```

Агент пишет **needles / intent**; apatch оркестрирует governed cycle и оставляет воспроизводимый ledger.

## Где аналогия сильна, где ломается

### Структурное сходство (сильно)

Классический compiler / build graph:

```text
Source → IR → Transform → Verify → Artifact
```

apatch spine:

```text
Needles / SPEC → Execution plan → Apply → Diagnose → Verify → Attest
```

Параллельно:

```text
Agent intent          Source
      ↓                   ↓
Needles               IR / deps graph
      ↓                   ↓
Mutation plan         Compile / transform
      ↓                   ↓
Apply                 Emit / link
      ↓                   ↓
Diagnose              Compiler diagnostics
      ↓                   ↓
Verify                Tests / link gate
      ↓                   ↓
Attest                Signed artifact
```

Особенно близко к **современным build-системам** (Bazel, Buck, Pants, Nix): там давно «компилируют» не только код, а **граф артеfactов и зависимостей** — apatch делает то же для agent-driven мутаций + provenance.

### Семантическое расхождение (ломается)

| | Compiler | apatch |
|---|----------|--------|
| Вход | program | intent |
| Выход | **equivalent** program (C++ → machine code, семантика сохранена) | **new state** репозитория |
| Исходник | обычно не мутируется | **мутируется** (это цель) |

```text
Compiler:     program  →  equivalent program     (semantics preserved)
apatch:       intent   →  state transition     (world changes)
```

Пример: SPEC «добавить rollback в spec_run» — после цикла **изменился** репозиторий. Компилятор так не работает.

**Diagnose** как раз **возвращает** силу compiler-аналогии: `no member named 'get_concept_name'` — тот же класс feedback, что у clang. Без unified diagnostics сравнение с build-runtime остаётся метафорическим; с [RFP-022](./RFP-022-unified-diagnostics-knowledge-graph.md) attested — это spine-слой (~90% build-fit в dogfood).

## Четыре метафоры — не смешивать

```text
  compiler       build system        migration engine    orchestrator
  ────────       ────────────        ────────────────    ────────────
  apatch compile Needles→Plan→       current state →     session_start
  (MD @sid)      Apply→Diagnose→     mutations →         spec_run, sandbox
                 Verify→Attest       new state           TrustChain, lanes
```

| Метафора | Fit | Что это в apatch | Типичная ошибка |
|----------|-----|------------------|-----------------|
| **Compiler (gcc/clang)** | ~50–55% | `apatch compile` + unified Diagnose (RFP-022) | «apatch = compiler» |
| **Build graph** | ~90% | spine: plan → apply → diagnose → verify → attest | JSONL назвать «LLVM IR» |
| **Migration engine** | ~80–90% | intent → mutations → new repo state | игнорировать verify/attest |
| **Governed transformation runtime** | ~100% | intent + sandbox + ledger + rollback | продавать как «patch tool» |
| **Orchestrator** | слой поверх | MCP, session, lanes — не заменяет build-metaphor | |

**Честная граница:** spine — **build / migration pipeline**; `apatch compile` — **отдельный compiler pass** для markdown semantic IDs.

## Канонический spine (цельная схема)

```text
Needles / SPEC     = source intent          (что и зачем менять)
       ↓
Execution plan     = mutation plan (JSONL)  (конкретные шаги: replace_file_content, …)
       ↓
Apply              = codegen / emit           (workspace mutation under lease)
       ↓
Diagnose           = compiler diagnostics     (clang/pytest/spec → structured findings)
       ↓
Verify             = linker + tests           (exit code gate: pytest, make, grep)
       ↓
Attest             = signed artifact          (Ed25519 + ledger provenance)
```

**Поверх spine (RFP-005/033):** `apatch probe` (falsify/regress/ratify) — слой *качества* самого Verify (гейт обязан уметь краснеть, иначе это театр); `apatch reality` — якорь *покрытия* над всем spine (наблюдаемая реальность → discharge → `uncovered` долг); `apatch scip impact` — advisory кросс-файлового refactor-impact на аттестованные требования. Это не шаги конвейера, а проверки доверия к нему.

Сопоставление с build-world:

```text
source  →  plan  →  emit  →  diagnostics  →  link/test  →  signed object
```

**Терминология:** JSONL после `generate_batch` — **execution plan** (mutation plan), не классический IR. В IR обычно есть промежуточная семантика и optimization passes; здесь шаги уже почти исполняемые (`replace_file_content`, Add File, …). Точнее:

```text
Needles → Execution Plan → Apply Runtime → Diagnose → Verify → Attest
```

`apatch_simulate` — dry-run plan (preflight risk map), аналог «plan-only build».

## Proof engine (Human Capital narrative)

Большинство систем отвечают: **что изменилось?**

apatch заточен под вопросы attributable work:

| Вопрос | Механизм |
|--------|----------|
| Кто инициировал? | TrustChain `signed_by`, session `intent` |
| На основании чего? | `artifacts[]`, SPEC `spec:ID#Rk`, needles / manifest |
| Чем проверено? | `verify_run` command + baseline + diagnostics artifacts |
| Чем подписано? | `apatch_attest`, incremental notarization, coverage |

```text
needles / manifest  →  intent surface
verify + diagnose   →  evidence surface
attest + trustchain →  provenance surface
```

Это **менее насыщенный рынок**, чем AI coding tools — и ближе к HC Platform (Contribution Vector для software): auditable substrate, не scoring/FIO mapping.
